# 팀원용 AI 지침 프롬프트

팀원이 쓰는 AI 도구(ChatGPT 프로젝트, Claude 프로젝트, Copilot 등)의 **프로젝트 지침·커스텀 인스트럭션 칸에 아래 블록을 그대로 붙여넣는다.**

`AGENTS.md`와 `CLAUDE.md`는 저장소를 직접 읽는 도구에만 전달된다. 웹 채팅에 코드를 복사해 붙여 쓰는 방식에는 전달되지 않아서, 같은 내용을 붙여넣을 수 있게 따로 둔 것이다.

이 문서를 고치면 팀원에게 다시 붙여넣으라고 알려야 한다. 규칙 자체는 `AGENTS.md`·`CLAUDE.md`가 기준이고, 이 문서는 그 요약이다. **둘이 어긋나면 저장소 문서가 맞다.**

---

## 붙여넣을 내용 (여기서부터)

### 프로젝트

드래곤 타워 — 드래곤을 육성해 탑에 도전하는 싱글 플레이 게임. Windows 바탕화면 위 오버레이로 동작한다.
C++17 + CMake, **게임 엔진 없음**, 필요하면 Win32 API + GDI+를 직접 쓴다. 저장소는 `1rkdwnsgh1/dragon-tower`, 3명이 함께 개발한다. 현재 v0.7.

코드 식별자는 영어, 주석과 문서는 한국어로 쓴다.

### 작업 전에 읽을 문서

위치를 찾으려고 파일을 넓게 뒤지지 말고 **`docs/codemap.md`(무엇이 어디에 있는지 적은 표)를 먼저 본다.** `src/win/Renderer.cpp`는 약 1060줄, `src/core/World.cpp`는 약 680줄이라 통째로 읽으면 안 된다. 지도에서 함수 이름을 찾아 `grep` 하고 그 근처만 읽는다.

| 문서 | 무엇이 들어 있나 |
|---|---|
| `docs/codemap.md` | **무엇이 어디에 있는지. 코드 찾기 전에 여기부터.** |
| `docs/game-design.md` | 통합 기획서. **규칙의 유일한 기준.** 확정 사항과 미결정 사항 |
| `docs/roadmap.md` | 개발 단계와 체크포인트, 현재 진행 상황 |
| `docs/implementation-notes.md` | 임시로 정한 수치, Windows에서 확인할 것 |
| `docs/changelog.md` | 버전별 바뀐 점과 저장 파일 호환 여부 |
| `docs/character-pipeline.md` | 캐릭터 이미지·애니메이션·스킬 적용 규격 |
| `docs/ai-workflow-notes.md` | AI 작업 비용 측정과 개선 |
| `assets/dragons/README.md`, `assets/enemies/README.md` | 드래곤·적 추가하고 그림 넣는 방법 |
| `AGENTS.md`, `CLAUDE.md` | 문서 규칙과 개발 지침 (이 프롬프트의 원본) |

기획서의 **"아직 미결정" 항목은 임의로 정하지 말고 사람에게 물어본다.** 정해지면 기획서를 갱신한다.

### 파일 구조

```
src/core/        게임 규칙 (플랫폼 무관, Linux에서도 빌드·테스트됨)
                 Game, World, Species, Enemy, Progression, SaveData, DragonData, EnemyData
src/win/         Windows 오버레이·그리기 (진입점 main.cpp)
                 App(창·입력·트레이), Renderer(그리기·UI), Sprites(시트 적재), Platform(OS 기능)
include/core/    공유 헤더. 조정 가능한 수치는 전부 Config.h
assets/dragons/<키>/   드래곤별 dragon.txt + 스프라이트 시트
assets/enemies/<키>/   적별 enemy.txt + 스프라이트 시트
tools/make_sheet.py    그림 → 스프라이트 시트 변환
tests/                 core_tests.cpp(규칙 검증), balance_sim.cpp(밸런스 시뮬레이션)
docs/                  기획서·로드맵·변경 기록
```

**중요한 분리**: 게임 규칙은 `src/core`에, OS 의존 코드는 `src/win`에 둔다. 규칙을 `src/win`에 넣으면 테스트할 수 없게 된다.

**수치는 코드에 박지 않는다.** 조정 가능한 값은 `include/core/Config.h`의 `cfg::` 상수로, 드래곤·적의 능력치와 행동은 `dragon.txt`·`enemy.txt`로 뺀다. 그래야 코드를 고치지 않고 밸런스를 바꿀 수 있다.

### 깨지면 안 되는 핵심 규칙

- **영구 사망**: 죽은 개체는 어떤 경로로도 부활 불가. 사망 확정 시점에 즉시 저장
- **탑에서는 자동 사냥 불가**
- **소리 금지**: 모든 상태·위험은 시각적 수단으로만 전달 (트레이 풍선 알림도 소리 없이)
- **클릭 통과(확정)**: 입력을 켜도 우리가 그린 것 위에서만 입력을 받고 나머지는 통과시킨다
- **오버레이 동작(확정)**: 드래곤·몬스터는 일반 창보다 항상 위. 다른 앱 전체화면이면 숨기되 자동 사냥은 계속 진행(숨김 ≠ 일시정지)
- **바탕화면 전투는 맨 아래 띠에서만**: 적은 왼쪽 밖에서 들어오고 목표는 드래곤
- **적 공격은 항상 예고 후 판정** — 이유를 알 수 없는 죽음이 생기면 수치 조정보다 먼저 고친다
- **자동 사냥 경험치 상한은 v0.5에서 껐다**(`cfg::kAutoExpCapEnabled = false`). 자르는 계산과 저장 필드는 되돌릴 수 있게 **지우지 말고 남겨 둔다**
- **저장 파일 호환**: 저장 형식에 키를 추가할 때 모르는 키는 조용히 넘기게 해서 이전 저장 파일이 그대로 읽히게 한다

### 작업 방식

- **로드맵 단계를 건너뛰지 않는다.** 각 단계의 "체크" 항목은 사람이 직접 실행해 확인한 뒤 다음으로 넘어간다
- 완성 코드를 한꺼번에 쏟지 말고 **눈으로 확인 가능한 최소 단위로 쪼갠다**
- 투명 창·항상 위·클릭 통과·전체화면 감지 같은 OS 의존 기능은 본 구현 전에 작은 실험으로 먼저 검증한다
- **`main`에 직접 커밋하지 않는다.** 브랜치를 만들어 PR로 올린다. 커밋 메시지에 단계·버전을 적는다 (예: `v0.4: 몬스터 4종과 적 폴더 구조`)
- 브랜치를 오래 열어 두지 않는다. 같은 문서를 건드리면 병합 충돌이 커진다
- **새 기능 요청을 받으면 먼저 기존 코드에 얼마나 들어 있는지 확인하고 알려 준다.** 요청의 절반이 이미 구현돼 있던 적이 있다

### 작업이 끝나면 갱신할 문서

코드를 고쳤으면 같은 PR에서 아래를 함께 고친다. 나중에 하면 안 한다.

1. **`docs/codemap.md`** — 함수·파일이 바뀌었으면 표도 고친다 (가장 자주 빠뜨린다)
2. **`docs/changelog.md`** — 추가/바뀜/고침과 **저장 파일 호환 여부**. 버전은 "밖에서 보이는 변화" 기준
3. **`docs/implementation-notes.md`** — 임시로 정한 수치가 바뀌었으면 표를 고친다. Windows에서 확인할 것이 생기면 목록에 추가
4. **`docs/game-design.md`** — 미결정이 결정됐거나 확정 사항이 바뀌었으면. 바꿀 때는 **본문을 지우지 말고 "바뀐 확정 사항" 절에 적고, 원래 장 맨 위에서 그쪽으로 안내한다**
5. **`docs/roadmap.md`** — 단계가 끝났거나 체크 항목이 무효가 됐으면
6. **`README.md`, `CLAUDE.md`** — 현재 버전 줄
7. 새 문서를 만들면 **`AGENTS.md`의 문서 목록에 추가한다**

**중복 금지**: 같은 결정은 한 곳에만 쓰고 나머지에서는 링크한다. 같은 내용이 두 곳에 있으면 한쪽이 반드시 낡는다.

### 토큰·비용 아끼는 법 (실제 측정 결과)

v0.2 세션에서 요청 156번을 측정했더니 **기본 지시문이 67.6%, 파일 읽기·명령이 24.1%, 실제 대화는 6.9%**였다. 요청을 한 번 주고받을 때마다 지침과 도구 설명이 통째로 다시 읽힌다. **비용은 한 번에 한 일의 양이 아니라 주고받은 횟수에 비례한다.**

- **코드 지도부터 본다.** 위치를 찾으려고 파일을 넓게 읽지 않는다
- **서로 상관없는 명령은 한 번에 묶는다.** `&&`나 `;`로 이어서 실행한다. 빌드·테스트·확인을 세 번에 나누지 않는다
  `cmake -S . -B build && cmake --build build -j && ctest --test-dir build --output-on-failure`
- **한 파일에서 고칠 곳이 여럿이면 한 번에 고친다.** 같은 파일을 여러 번 열고 닫지 않는다
- **중간 보고를 줄인다.** 단계마다 설명하지 말고 끝난 뒤 한 번에 정리한다
- **되돌리기 쉬운 일은 묶어서 맡긴다** ("A 하고 되면 B도")
- **주제가 바뀌면 새 대화를 시작한다.** 대화가 길어지면 앞 내용을 계속 다시 읽는다
- **사람이 정해야 할 것은 미루지 말고 처음에 모아서 묻는다.** 다 만든 뒤 방향이 바뀌면 그만큼 다시 한다

### 자주 틀렸던 것 (같은 실수 반복 금지)

- **지금 팀이 실제로 어떻게 작업 중인지 먼저 묻는다.** 캐릭터 방향을 왼쪽으로 정해 문서·템플릿·스크립트를 다 만든 뒤에 팀원들이 이미 오른쪽으로 그리고 있다는 걸 알았다. 전부 다시 고쳤다
- **확인 전에 "못 한다"고 판단하지 않는다.** 에셋이 Git LFS에 있어 못 받는다고 넘겨짚었는데 `git lfs pull` 하면 바로 받아졌다
- **출력이 이상하면 그 자리에서 원인을 확인한다.** 한글이 깨져 보이는 걸 넘겼다가 다음 버전에서 `printf("%s")`에 `std::string`을 넘기는 회귀를 발견했다
- **이미지를 자르거나 변환했으면 결과를 눈으로 확인한다.** 성공 메시지만으로는 모른다. 2048×1024 시트를 128칸으로 잘못 봐서 엉뚱한 칸을 자르고도 "성공"이라고 나왔다
- **크기·비율은 눈대중하지 말고 같은 부위를 숫자로 잰다.** 윤곽 전체로 재면 날개 펼침에 휘둘려 반대 결과가 나온다
- **긴 글(PR 본문·커밋 메시지)은 셸 인자로 넘기지 않는다.** 백틱이 명령으로 실행된다. 파일(heredoc)에 쓴 뒤 파일을 넘긴다

### Windows 코드에서 특히 조심할 것

`src/win`은 Windows에서만 컴파일된다. 리눅스·맥에서는 `src/core`와 테스트만 빌드된다. 그래서 다음 세 가지를 CI 실패로 알게 된 적이 있다 — 푸시 전에 훑어본다.

1. **헤더에 쓰는 타입은 헤더에서 포함한다.** `App.h`에 `shellapi.h`가 없어 `NOTIFYICONDATAW`를 인식하지 못했다
2. **`RectF` 모호성**: `App.cpp`에서 그냥 `RectF`라고 쓰면 우리 타입 `dt::RectF`로 해석된다. GDI+ 타입이 필요하면 `Gdiplus::RectF`로 명시한다
3. **파일 안의 정의 순서**: 선언 전에 쓰면 안 된다

### 빌드와 실행

```powershell
cmake -S . -B build
cmake --build build
```

실행 파일은 `build/Debug/dragon_tower.exe` (생성기에 따라 `build/dragon_tower.exe`).
저장 파일은 `%APPDATA%\DragonTower\save.txt`.
