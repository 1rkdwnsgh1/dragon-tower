# 토큰 절약 — 조사 인계 문서

2026-11-16 밤 드래곤 타워 세션의 실측과 그 세션에서 실제로 생긴 문제를 정리했다.
**다른 세션에서 이걸 들고 더 깊이 파기 위한 문서다.** 결론을 베껴 쓰지 말고, 아래
"조사할 것"의 질문에 답하는 방식으로 쓸 것.

출처 표기 규칙: **[1차]** = Anthropic 공식 문서·엔지니어링 블로그, **[2차]** = 외부 블로그·기사
(수치의 1차 자료를 확인하지 못함). 2차 수치는 그대로 믿지 말 것.

## 1. 실측 — 토큰이 실제로 어디로 갔나

드래곤 타워 저장소에서 "스킬 이펙트 적용 계획 수립 + 예약 작업 생성" 한 세션.

| 항목 | 값 |
|---|---|
| 요청(왕복) 수 | 43회 |
| 캐시 읽기 | 8,278,189 토큰 |
| 캐시 쓰기 | 100,689 토큰 |
| 출력 | 39,265 토큰 |
| 순수 입력 | 86 토큰 |
| 비용 가중 환산 | 약 1,225,000 토큰분 |

가중치: 캐시 읽기 ×0.1, 캐시 쓰기 ×2, 출력 ×5, 입력 ×1.

### 비중

| 그룹 | 비중 | 호출 수 |
|---|---|---|
| **지시문**(시스템 프롬프트 + 도구 목록 + `CLAUDE.md` + 첨부) | **66.2%** | — |
| 파일·명령 (`Bash` 28 / `Write` 1 / `Edit` 1) | 20.4% | 30 |
| 대화 자체 (내 답변·사고 7.4% + 사용자 0.2%) | 7.6% | — |
| GitHub·예약 연결 (`mcp__claude-code-remote`) | 2.9% | 3 |
| 그 외 (`Projects` 2.3, 태스크·스킬 0.7) | 3.0% | 11 |

**읽은 양이 아니라 주고받은 횟수가 비용을 정했다.** 지시문은 턴마다 다시 읽히므로
43번 재읽혔다. 답변을 짧게 써서 아끼는 건 7.6% 안에서의 다툼이라 거의 의미가 없다.

측정의 한계: 사용량은 **요청 단위로만** 측정되고 도구 단위로 나뉘지 않는다. 위 그룹별
비중은 추정이다.

### 조사할 것

- 그룹별 추정은 어떤 방식으로 배분되는가? 한 요청에 도구 호출이 여럿이면 어떻게 쪼개지는가?
- 캐시 읽기 8,278,189 / 43회 = 요청당 약 19만 토큰. 캐시 TTL 과 캐시 적중률을 어떻게 재는가?
  캐시가 깨지는 조건(어떤 변경이 prefix 를 무효화하는가)을 명확히 할 것 — 이게 아래 ⑤의 판단 근거다.
- "요청 수를 줄이면 지시문 비용이 비례해 줄어든다"가 캐시 가격 체계에서도 성립하는가?
  (캐시 읽기는 싸므로, 왕복을 줄이는 효과가 비가중 토큰 수보다 작을 수 있다.)

## 2. 오늘 실제로 생긴 문제와 해결책

이 절이 이 문서의 핵심이다. 일반론이 아니라 **그 세션에서 벌어진 일**이다.

### 문제 1 — `Bash` 를 28번 불렀다

저장소 `CLAUDE.md` 가 "상관없는 명령은 `&&` 로 묶어라"라고 적어 뒀는데 절반만 지켰다.
묶을 수 있었던 것: `git rev-parse` + `ls` + `git branch` (3→1), CI 1차 확인 + 폴링 루프 (2→1),
이미지 치수 확인 + 경로 확인 (2→1).

**해결**: 한 세션의 `Bash` 호출에 상한을 정하고(예: 10회) 명령을 `&&`·`;` 로 잇는다.
28→10이면 지배적 비용인 지시문 재읽기도 같이 3분의 1 이하로 준다.

**단, 이 해결이 문제 5를 낳았다 — 아래를 반드시 같이 읽을 것.**

### 문제 2 — 도구 출력을 날것으로 받았다

PR 의 변경 파일 목록(415개)을 조회할 때, 2~5페이지는 `awk` 로 폴더만 추렸는데
**1페이지는 파일명 100줄을 그대로 받았다.** 그 100줄이 세션 끝까지 context 에 남았다.

**해결**: 조회 도구의 출력은 **받기 전에** 줄인다.
- `gh api ... -q '...'` (jq 표현식을 서버가 아니라 CLI 단계에서 적용)
- 목록은 `awk -F/ '{print $1"/"$2}' | sort -u` 로 집계만
- 원칙: **"세어 보려면 세는 명령을 쓰고, 목록을 가져오지 않는다."**

### 문제 3 — 무거운 읽기를 직접 했다

`CLAUDE.md`, `docs/codemap.md`, `docs/characters/revenant-dragon-zone-skills.md` 를
내 context 에 쌓았다. 그런데 zone-skills 문서에서 실제로 필요한 건 **"11/15 결정이
`dragon.txt` 에 반영됐는가" 한 줄**이었다.

**해결**: 넓게 훑어야 하는 조사는 별도 context 를 쓰는 서브에이전트에 넘기고 결론만 받는다.
**[1차]** 서브에이전트는 자기 context 에서 읽고 최종 요약만 반환한다.
**주의**: **[1차]** 서브에이전트도 `CLAUDE.md`·MCP·스킬을 자기 몫으로 다시 로드하므로
토큰은 대략 팀 크기에 비례한다. **한두 번 읽으면 끝나는 것에 쓰면 손해다.**

조사할 것: 손익분기점은 어디인가? "읽을 파일 N개 이상, 또는 예상 출력 M 토큰 이상이면
서브에이전트"라는 기준을 세울 수 있는가?

### 문제 4 — 질문 라운드를 코드 조사보다 먼저 돌렸다

`grill-me` 로 4라운드를 돌렸다. 질문 품질에는 값을 했다 — **버려질 스킬에 이펙트를 붙이려던
것을 1라운드에서 잡았다**(11/15 결정으로 없어질 `Zone` 스킬). 하지만 3라운드의
"좌우 뒤집기를 어떻게 구현하나"는 **코드를 읽고 나서야 답이 작아졌다**(이미 flip 인자가 있었다).
조사를 먼저 다 하면 라운드가 4→2로 줄었다.

**해결**: 질문을 만들기 전에 **환경에서 확인 가능한 사실은 전부 먼저 확인한다.**
사람에게 물을 것은 "결정"뿐이고 "사실"은 내 일이다. 라운드 수 = 왕복 수 = 지시문 재읽기 횟수다.

### 문제 5 — `&&` 로 묶다가 CI 실패를 무시하고 머지했다

문제 1의 해결(명령 묶기)을 적용하면서 이렇게 썼다:

```bash
for i in $(seq 1 8); do sleep 45; R=$(...); if ! echo "$R" | grep -qE 'in_progress'; then echo "$R"; break; fi; done \
  && gh api .../merge -X PUT ...
```

폴링 루프는 **"확인이 끝났다"로 정상 종료**한다. CI 가 실패해도 종료 코드는 0이므로
`&&` 뒤의 머지가 실행됐다. **CI 실패 상태로 PR 을 머지했다.**

**해결**: `&&` 는 "앞이 성공해야 뒤를 한다"를 뜻하지만, **앞의 성공이 내가 원하는 판정과
같은지 확인해야 한다.** 판정을 종료 코드로 끌어올릴 것:

```bash
# 결론을 종료 코드로 만든다
echo "$R" | grep -q 'failure' && { echo "CI 실패 — 머지하지 않는다"; exit 1; }
echo "$R" | grep -qE 'in_progress|queued' && { echo "CI 미완 — 머지하지 않는다"; exit 1; }
gh api .../merge -X PUT ...
```

**교훈**: 토큰을 아끼려고 명령을 묶는 것과, 게이트를 지키는 것은 **충돌할 수 있다.**
묶는 대상은 *조회*로 한정하고, **되돌릴 수 없는 동작(머지·푸시·삭제)은 묶지 않는다.**

### 문제 6 — 이미 적힌 결정을 놓칠 뻔했다

`docs/characters/` 안에 "7. 결정 (2026-11-15, 사람)" 절이 있었고, 그 결정이 아직
데이터에 반영되지 않은 상태였다. 기획서(`game-design.md`)만 봤으면 못 찾았다.

**해결**: 작업 시작 전에 **"결정"·"확정"·"미결정" 같은 낱말로 저장소 전체를 한 번 grep**
한다. 이건 토큰을 쓰는 쪽이지만, **버릴 작업을 막는 값이 훨씬 크다.** 토큰 절약의 최대 항목은
"안 해도 될 일을 안 하는 것"이다.

## 3. 기법 정리 — 효과가 큰 순서

### ① Programmatic Tool Calling (프로그래매틱 도구 호출) **[1차]**

Claude 가 도구를 JSON 으로 하나씩 부르는 대신, **코드 실행 환경 안에서 코드가 도구를 호출**한다.
토큰이 줄어드는 이유 세 가지:
- 프로그래매틱 호출의 **도구 결과가 Claude 의 context 에 들어가지 않는다.** 코드의 최종 출력만 들어간다.
- 한 번의 코드 실행에서 도구를 여러 번 부른다 → 모델 왕복이 사라진다.
- if 문 판단을 모델이 아니라 실행 환경이 한다 → 첫 토큰까지의 지연도 줄어든다.

수치: 도구 75개 프로젝트 관리 에이전트 벤치마크에서 **과금 입력 토큰 약 38% 감소, 정확도 변화 없음**.
복잡한 리서치 과제에서 평균 43,588 → 27,297 토큰(37%).

주의 **[2차]**: 모델이 필터링 코드를 많이 쓰면 오히려 늘 수 있다는 관찰이 있다
(가격 가중 토큰이 증가한 사례). 코드 복잡도와 절감의 균형을 봐야 한다.

**오늘 세션에 대응되는 지점**: 문제 2(파일 목록 415개). 목록을 context 로 가져오지 말고
스크립트가 세어 결과만 돌려주는 패턴이 정확히 이것이다.

### ② Code execution with MCP **[1차]**

MCP 서버를 "도구 목록"이 아니라 **코드 API** 로 다룬다. 에이전트가 파일 시스템을 돌아다니며
필요한 정의만 읽는 **점진적 공개(progressive disclosure)** 가 핵심이다.
Google Drive → Salesforce 워크플로를 코드로 재작성해 **150,000 → 2,000 토큰(98.7%)**.
"에이전트가 10,000 행이 아니라 5 행을 본다"가 요지다.

비용: 에이전트가 생성한 코드를 안전하게 실행할 환경이 필요하다 — 그 자체로 복잡도가 생긴다.

### ③ Tool Search Tool **[1차/2차]**

도구 정의를 전부 미리 올리지 않고 필요할 때 검색해 쓴다. MCP 평가에서 **85% 토큰 감소** (2차 수치).
**오늘 세션은 이미 이 방식이었다** — deferred 도구 목록이 그것이고, 덕분에 도구 목록이
더 커지지 않았다. 지시문 66% 안에서 도구 목록이 차지하는 몫을 재 볼 가치가 있다.

### ④ Context editing — 도구 결과·사고 블록 지우기 **[1차]**

| 전략 | 식별자 | 동작 |
|---|---|---|
| 도구 결과 지우기 | `clear_tool_uses_20250919` | 입력이 임계값(기본 100,000 토큰)을 넘으면 오래된 도구 결과를 지우고 최근 것만 남긴다(`keep` 기본 3) |
| 사고 블록 지우기 | `clear_thinking_20251015` | 지난 턴의 사고 내용을 지운다. 최근 것은 보존 선택 가능 |
| 메모리 도구 | `memory_20250818` | context 밖 파일 시스템에 저장하고 꺼내 쓴다. 세션 간 지속 |

수치: 100턴 웹 벤치마크에서 **편집만으로 성능 +29%, 메모리 도구까지 +39%, 토큰 84% 절감**
(2차 정리이나 Anthropic 벤치마크 인용).

**대가 두 가지**:
1. 지운 내용이 다시 필요하면 **도구를 또 불러야 한다.**
2. **지우는 행위가 프롬프트 캐시를 무효화한다.** 그래서 `clear_at_least`(한 번에 최소 몇 토큰을
   지울지) 설정이 캐시 경제성 때문에 중요하다고 문서가 명시한다.

**오늘 세션에는 권하지 않았다**: 캐시 읽기가 828만 토큰(가중 후에도 최대 항목)인 구조에서
캐시를 깨는 쪽이 더 비쌀 수 있다. **이건 100턴급 장시간 세션용이다.**

조사할 것: 캐시 읽기 단가 ×0.1 과 캐시 재작성 ×2 를 놓고, **몇 턴 이상이면 context editing 이
이득인가?** 손익분기 턴 수를 실제 가격으로 계산할 것. 이게 이 문서에서 가장 답이 필요한 질문이다.

### ⑤ 서브에이전트에 무거운 읽기 넘기기 **[1차/2차]**

"가장 싼 context 는 애초에 안 읽는 context." 별도 context 에서 읽고 요약만 반환.
대가: 에이전트마다 `CLAUDE.md`·MCP·스킬을 다시 로드하고, 스폰 프롬프트에 넣은 것이
처음부터 context 에 쌓인다 → **토큰은 팀 크기에 비례.**

### ⑥ 세션 운용 명령 **[1차/2차]**

- `/context` — 무엇이 얼마나 로드됐는지, **MCP 서버별로** 보여 준다. **여기서부터 시작할 것.**
- `/compact` — 대화를 요약으로 압축. `/compact Focus on code samples and API usage` 처럼
  무엇을 보존할지 지시할 수 있다. `CLAUDE.md` 에 compact 지침을 미리 적어 둘 수도 있다.
- `/clear` — 작업이 바뀌면 비운다. "다시 설명하는 비용 < 죽은 context 를 끌고 가는 비용."
- `/rewind`, `/recap` — 2차 자료가 언급하는 명령. 실존·동작을 1차 문서로 확인할 것.

**오늘 세션에 대한 가장 확실한 한 수**: `/context` 로 재 보고 **안 쓰는 MCP 서버를 끄는 것.**
Notion·Google Drive·Claude Docs 가 붙어 있었는데 한 번도 쓰지 않았다. 2차 자료는 쓰지 않는
MCP 서버 비활성화로 25~47% 절감을 주장한다.

**미해결 문제**: 예약 작업(scheduled task)에 붙은 MCP 연결은 작업 설정에 저장되어 있고,
프롬프트에서 "쓰지 마라"고 적어도 **도구 정의는 계속 로드된다.** 프롬프트 수정 API 로는
연결을 떼지 못했다. → 조사할 것: 예약 작업의 MCP 연결을 떼는 방법이 UI 설정 말고 있는가?

### ⑦ `CLAUDE.md` 줄이기 **[2차]**

3,847 토큰짜리를 500 토큰 아래로 줄여 **91.9% context 감소에 품질 저하 없음**이라는
벤치마크(token-optimizer 저장소)가 있다.

**이 저장소에는 그대로 권하지 않는다.** 드래곤 타워 `CLAUDE.md` 는 약 2,600 토큰이고
43번 재읽혔지만, 그 안의 "깨지면 안 되는 핵심 규칙"(영구 사망, 클릭 통과, 소리 금지)이
매 턴 들어오는 덕에 규칙 위반이 없었다. **줄이면 안전이 깎인다.**
타협안: "AI 도구에게: 적게 주고받기" 같은 **반복 안내 성격의 절만** 별도 문서로 빼고 링크를 남긴다.

조사할 것: 그 벤치마크가 측정한 "품질"이 무엇인가? 규칙 준수율을 포함했는가, 아니면
코드 생성 품질만인가? 후자라면 이 저장소에는 적용되지 않는다.

### ⑧ 외부 도구 — 근거가 약하다 **[2차]**

| 도구 | 주장 | 평가 |
|---|---|---|
| `context-mode` (오픈소스 MCP 플러그인) | MCP 출력을 샌드박스 지식베이스로 색인하고 요약만 올려 **MCP 토큰 출력 50~90% 감소** | 블로그 한 곳. 1차 자료 미확인 |
| RTK (Rust Token Killer) | `PreToolUse` 훅으로 Bash 명령을 압축형으로 치환, 흔한 개발 명령에서 **60~90% 절감** | 같음. 3명이 쓰는 저장소에 훅을 넣는 리스크 |
| `caveman` 플러그인 | 극도로 압축된 응답 강제 / `CLAUDE.md` 를 압축 문법으로 재작성 | 출력은 전체의 7.6%뿐이라 효과가 작다 |
| `.claudeignore` | 읽기 대상 제외로 **50~70% 절감** | 2차. 다만 개념 자체는 타당하고 리스크가 낮다 |

**조사할 것**: `context-mode` 와 RTK 의 저장소를 직접 열어 벤치마크 재현 방법이 공개돼 있는지
확인할 것. 재현 코드가 없으면 수치를 인용하지 말 것.

## 4. 다음 세션에서 답할 질문 (우선순위)

1. **context editing 의 손익분기 턴 수.** 캐시 읽기 ×0.1 vs 캐시 무효화 ×2 를 실제 단가로
   계산해, 몇 턴/몇 토큰 이상이면 이득인지 숫자로 낼 것. (이 세션: 43턴, 캐시 읽기 828만)
2. **지시문 66% 의 내부 구성.** `/context` 로 시스템 프롬프트 / 도구 목록 / `CLAUDE.md` /
   MCP 서버별 비중을 쪼갤 것. 가장 큰 덩어리를 먼저 공격해야 한다.
3. **서브에이전트 손익분기.** 파일 N개·출력 M 토큰 기준을 세울 것.
4. **예약 작업의 MCP 연결을 프로그램으로 떼는 방법.** 없으면 "작업 생성 시 연결을 고르는
   방법"을 찾을 것.
5. **Programmatic Tool Calling 을 이 환경에서 쓸 수 있는가.** Claude Code 세션에서
   사용 가능한지, 아니면 API 직접 호출 전용인지 확인할 것.
6. `/rewind`·`/recap` 의 실존과 정확한 동작 (2차 자료만 봄).
7. **`CLAUDE.md` 축약 벤치마크의 "품질" 정의.** 규칙 준수율을 포함하는지.

## 5. 당장 적용한 것 (드래곤 타워 저장소)

`docs/auto-queue-2026-11-16.md` 에 "주고받는 횟수를 줄이는 규칙" 6개를 넣었다 (PR #66).
11회차가 같은 절차를 반복하므로 효과가 11배다.

1. 명령은 `&&` 로 묶고 한 회차 `Bash` 호출 10회 이하 — **단 되돌릴 수 없는 동작은 묶지 않는다**
2. 도구 출력은 `-q`·`awk`·`sort -u` 로 걸러 받는다
3. 넓은 조사는 `Explore` 서브에이전트, 한두 번 읽을 것엔 쓰지 않는다
4. 큰 파일은 `codemap.md` 로 위치를 찾아 `grep` 으로 근처만
5. 중간 보고 생략, 회차 끝에 3줄
6. 안 쓰는 MCP 연결(Notion·Drive·Docs)은 쓰지 않는다

넣지 않은 것: `CLAUDE.md` 축약(안전 규칙이 깎인다), context editing(캐시 경제성),
외부 훅 도구(근거 부족 + 공동 저장소 리스크).
