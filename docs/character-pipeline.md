# 캐릭터 이미지·애니메이션·스킬 적용 기획

상태: 초안 · 2026-11-13. **확정**, **현재 구현**, **제안(미확정)**을 구분한다. 제안은 팀 검토 후 확정하고 이 문서를 갱신한다. 코드는 아직 바꾸지 않았다.

## 1. 확정 사항

- 캐릭터 애니메이션은 **스프라이트 시트 이미지**로 적용한다.
- 팀원 3명이 드래곤을 **1인 1종**씩 만든다. 첫 제작 목표는 3종이다. 어떤 3종인지(기존 화염·대지·바람·물 후보, [망령룡](characters/revenant-dragon.md) 포함 여부)는 미정이다.
- 이후 드래곤을 **추가하기 쉬운 구조**로 만든다. 새 드래곤 추가 시 기존 드래곤 파일과 다른 팀원의 작업을 건드리지 않는 것을 목표로 한다.

## 2. 현재 구현 (2026-11-13 main 기준)

| 항목 | 현재 방식 | 추가를 어렵게 하는 점 |
|---|---|---|
| 이미지 | 종류마다 정지 PNG 1장. 게임이 위아래로 흔들어 움직임 표현 | 애니메이션 없음 |
| 이미지 목록 | `src/win/Sprites.cpp`의 `kSpriteKeys`에 파일 이름을 직접 나열 | 새 파일마다 코드 수정 |
| 드래곤 종류 | `include/core/Species.h`의 `enum Species`(4개)와 `kSpeciesCount = 4` | 종류 추가 시 enum·개수·배열 동시 수정 |
| 능력치·스킬 | `src/core/Species.cpp`의 고정 배열에 4종을 한곳에 작성 | 3명이 같은 파일을 고쳐 충돌 가능 |
| 스킬 동작 | `SkillKind` 8종(유도탄·원형·직선·돌진·회복·방패·가속·장판) + 수치 | 수치만 다른 스킬은 쉽게 추가 가능(장점) |
| 도감 저장 | `SaveData::speciesSeen[kSpeciesCount]` 고정 배열. 개체 종류는 영문 키로 저장 | 종류 수가 바뀌면 배열 크기 변경 필요. 키 저장은 유지할 장점 |

이미지 파일 규격은 [assets/README.md](../assets/README.md)를 따른다. 이 문서는 그 규격에 애니메이션과 캐릭터별 구성을 더하는 계획이다.

## 3. 제안: 드래곤 1종 = 폴더 1개

드래곤마다 폴더 하나에 데이터와 이미지를 모은다. 게임은 시작할 때 `assets/dragons/` 아래 폴더를 모두 읽어 드래곤 목록을 만든다. 새 드래곤은 폴더를 추가하는 것만으로 등록되는 것을 목표로 한다.

```
assets/dragons/
  fire/
    dragon.txt        # 이름, 역할, 능력치, 스킬 수치, 애니메이션 정보
    idle.png          # 상태별 스프라이트 시트
    move.png
    attack.png
    hit.png
    death.png
    skill_1.png       # 스킬 아이콘 (선택)
    fx_skill_1.png    # 스킬 효과 시트 (선택)
    CREDITS.md        # 제작자, 출처, 라이선스
  revenant/
    ...
```

- 폴더 이름 = 영문 키(`fire`, `revenant` 등). 저장 파일에도 이 키를 쓴다. 한 번 정한 키는 바꾸지 않는다(바꾸면 기존 저장의 개체를 찾지 못함).
- 코드의 `enum Species`와 고정 배열은 "키로 찾는 목록"으로 바꾼다. 도감도 키 목록으로 저장한다.
- 데이터 파일 형식은 **미결정**. 후보는 아래 두 가지다.
  - 기존 `save.txt`와 같은 `키=값` 텍스트: 외부 라이브러리가 필요 없다. 대신 중첩 구조(애니메이션·스킬 목록) 표현이 불편하다.
  - JSON: 구조 표현이 쉽다. 대신 헤더 하나짜리 파서(예: nlohmann/json)를 추가해야 해서 현재의 "외부 라이브러리 없음" 임시 결정과 충돌한다.

## 4. 제안: 스프라이트 시트 규격

| 항목 | 제안 |
|---|---|
| 배치 | 상태 1개 = PNG 1장. 프레임을 **가로 한 줄**로 같은 크기 칸에 배치 |
| 칸 크기 | 한 시트 안에서 모든 칸이 같다. 프레임 수 = 이미지 너비 ÷ 칸 너비 |
| 기준점 | 칸 안의 **발 위치(접지점)** 좌표를 데이터에 기록. 프레임마다 기준점이 같아야 흔들림이 없다 |
| 방향 | 오른쪽을 본다. 왼쪽은 좌우 반전. 반전하면 안 되는 캐릭터(예: 망령룡의 비대칭 날개)는 `flip=no`와 왼쪽 시트를 따로 둔다 |
| 재생 | 상태마다 초당 프레임 수와 반복 여부(대기·이동은 반복, 공격·피격·사망은 1회) |
| 배경 | 투명 PNG |

### 상태와 대체 규칙

| 상태 | 필수 여부 | 파일이 없을 때 |
|---|---|---|
| idle(대기) | 필수 | 정지 PNG → 그것도 없으면 임시 도형 |
| move(이동) | 권장 | idle 사용 |
| attack(공격·스킬 사용) | 권장 | idle 사용 |
| hit(피격) | 선택 | 현재처럼 깜빡임 효과만 |
| death(사망) | 선택 | 현재처럼 사라지는 효과만 |

대체 규칙이 있으면 팀원이 idle 하나만 먼저 넣고 바로 게임에서 확인할 수 있다. 나머지 동작은 순서대로 추가한다.

### 해상도

- 현재 드래곤의 화면 표시 높이는 약 102px이다. 원본은 크게 그려도 되지만 **게임에 넣는 시트는 표시 크기의 1~2배**(높이 약 128~256px)로 줄여서 넣는 것을 제안한다. 512 시트를 여러 장 넣으면 메모리와 GDI+ 그리기 부담이 커진다.
- 3명이 그림체를 맞추려면 칸 크기, 캐릭터가 칸을 차지하는 비율, 외곽선 두께를 미리 하나로 정해야 한다. 이 값은 **미결정**이다.

## 5. 제안: 스킬 적용 방식

- 스킬 **동작 종류**는 지금처럼 코드의 `SkillKind`를 쓴다. 드래곤 데이터 파일에는 종류 이름과 수치(위력, 범위, 재사용 대기시간, 습득 레벨)만 적는다.
- 기존 8종으로 표현되는 스킬은 코드 수정 없이 데이터만으로 추가한다.
- 새로운 동작이 필요한 스킬(예: 소환, 흡혈)은 `SkillKind`를 추가하는 **코드 작업**이며, 그 드래곤 담당자 혼자 결정하지 않고 팀이 함께 검토한다. 공통 규칙(공격 예고, 영구 사망, 탑 규칙)과 충돌하지 않는지 확인한다.
- 스킬 아이콘은 정지 이미지, 스킬 효과는 스프라이트 시트(선택)로 넣는다. 효과 시트가 없으면 현재 도형 효과를 쓴다.
- 스킬을 쓸 때 드래곤은 `attack` 상태를 재생한다. 스킬마다 다른 동작이 필요하면 이후 확장으로 검토한다.

## 6. 새 드래곤 추가 절차 (구조 완성 후)

1. `assets/dragons/<키>/` 폴더를 만들고 다른 드래곤 폴더의 `dragon.txt`를 복사해 수정한다.
2. `idle.png`를 넣고 게임에서 표시 크기와 기준점을 확인한다.
3. 나머지 상태 시트와 스킬 아이콘을 추가한다.
4. `CREDITS.md`에 제작자·출처·라이선스를 적는다. 생성형 AI를 썼으면 사용 도구를 적는다.
5. 캐릭터 기획 문서를 `docs/characters/<키>.md`에 둔다.
6. 다른 드래곤 폴더와 공통 코드는 고치지 않는다. 고쳐야 한다면 별도 PR로 팀과 상의한다.

## 7. 확인이 필요한 사항

- 첫 3종을 어떤 드래곤으로 할지. 기획서의 "드래곤 4종"과 1인 1종 3종의 관계
- 데이터 파일 형식(`키=값` 또는 JSON)
- 공통 칸 크기, 캐릭터 비율, 외곽선·채색 기준 등 3명이 공유할 그림 규격
- 상태별 최소 프레임 수와 재생 속도 기준
- [망령룡 작업 자료](characters/revenant-dragon-progress.md)는 왼쪽 지향이고 프레임이 낱장 PNG(ZIP)이다. 이 규격(오른쪽 지향, 가로 시트)으로 변환할지, 로더가 낱장도 받을지
- 일반 적과 보스에도 같은 폴더 구조를 쓸지
