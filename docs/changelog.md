# 버전별 바뀐 점

버전은 "밖에서 보이는 변화"를 기준으로 올린다. 저장 파일 형식이 바뀌면 호환 여부를 반드시 적는다.

**항목은 날짜 내림차순으로 맨 위에 쌓는다.** 두 사람이 같은 날 각자 쓰면 순서가 엉키기 쉬우니
(실제로 v1.8 항목이 11/15 묶음 아래에 끼어 있었다) 합칠 때 날짜를 확인한다.
번호를 붙이지 않은 항목도 있다 — 게임이 바뀌지 않은 문서·CI 작업이다.


2026-11-15 이전 항목은 [archive/changelog-2026-11-15-이전.md](archive/changelog-2026-11-15-이전.md) 로 옮겼다.
읽지 않는다 — 옛 버전의 변경 내역을 확인해야 할 때만 사람이 지시한다.

## 문서: 읽기 경로 개편 — 고정 읽기 336KB → 16KB (2026-11-17)

`AGENTS.md` 가 "어떤 작업이든 시작 전에 18개 문서를 모두 확인"하라고 적어 두었고, 그 18개 합계가
약 336KB(한글 약 11만 자)였다. 요청마다 지시문이 다시 읽히는 구조에서 이게 비용의 대부분이었다.
`CLAUDE.md` 의 "적게 주고받기"(넓게 읽지 말라)와도 정면으로 모순이었다.

### 바뀐 것

- **새 문서 셋**
  - `docs/STATE.md` — 현재 버전·CI·열린 PR·**막혀 있는 것**·순서 제약. 세션 시작 때 읽는 하나.
  - `docs/INDEX.md` — 작업별 라우팅 표 + **유일한 문서 색인**.
  - `docs/decisions.md` — 사람이 정한 것의 색인. 심의 문서를 내려도 결정은 여기 남는다.
- **`docs/archive/` 신설, 평시에 읽지 않는다** — 종료된 작업 큐 2개, 깊이감 심의 4종,
  망령룡 장판 심의, 2026-11-15 이전 변경 기록, 토큰 조사 원본. 227KB.
- **`AGENTS.md` 삭제** — 문서 규칙은 `CLAUDE.md` 로, 문서 목록은 `docs/INDEX.md` 로 합쳤다.
- **문서 목록을 한 곳으로** — README·`CLAUDE.md` 의 목록을 없애고 `docs/INDEX.md` 링크만 남겼다.
  세 곳에 나뉘어 13/18/5개로 서로 달랐다.
- **분리**: `implementation-notes.md` 의 Windows 확인 목록(212줄) → `docs/windows-checklist.md`.
  `changelog.md` 는 최근 이틀만 남기고 758줄을 archive 로.
- **`docs/token-budget.md`** — 토큰 줄이는 방법 중 **이 환경에서 쓸 수 있고 근거가 확인된 것만**.
  API 전용 기법(Programmatic Tool Calling·context editing 등)은 "쓸 수 없는 것"으로 분리해 적었다.
- **`tools/check_docs.py` + CI 0단계** — 깨진 상대 링크와 색인 미등재를 기계가 잡는다.

### 작업 중 생긴 문제

- **문서를 `archive/` 로 옮기자 안쪽 상대 링크 23개가 한꺼번에 깨졌다.** `git mv` 는 링크를
  고쳐 주지 않는다. 이번에는 스크립트로 일괄 수정했고, 재발을 막기 위해 `check_docs.py` 를 만들었다.
  **문서를 옮기는 PR 에서는 먼저 `python3 tools/check_docs.py` 를 돌린다.**
- `gh pr list` 는 이 환경에서 **403** 이다(GraphQL 차단). `gh api repos/.../pulls` 로 REST 를 쓴다.
- 결정 내용을 `decisions.md` 로 옮기면서 **같은 결정이 두 곳에 남을 위험**이 생겼다.
  게임 규칙 결정은 `game-design.md` 10장을 원본으로 두고 `decisions.md` 는 링크만 적는 쪽으로
  나눴다. 설계 방향 결정만 `decisions.md` 가 원본이다.

### 남은 위험

`STATE.md` 가 갱신되지 않으면 지금보다 나쁘다 — 낡은 상태 문서는 없는 것보다 해롭다.
`CLAUDE.md` 에 "작업을 끝낼 때 같은 PR 에서 고친다"를 넣었지만 이것은 기계가 잡지 못한다.

## 장판 스킬에도 효과 그림을 쓸 수 있다 — 저주의 안개 (2026-11-17)

게임 규칙은 바뀌지 않았다. 저장 파일도 **그대로 호환된다**.

**`Zone` 스킬이 `fx=` 를 쓸 수 있게 됐다.** `fx=` 를 적은 장판만 수명 전체를 덮는 효과를
하나 띄운다 — **안 적은 장판은 전과 똑같이** 그려진다.

저주의 안개에 퍼짐 10칸 + 유지 8칸을 이은 18장짜리 그림을 붙였다. 2026-11-15 에 망령의
침식이 안개로 합쳐졌으므로, 침식용으로 만들어 둔 그림이 곧 안개의 그림이다.

**주의**: 효과 길이는 `fx_windup`+`fx_hold`+`fx_tail` 로 정해진다. 장판 `duration` 과 맞추지
않으면 잔류가 장판이 사라진 뒤에도 남는다 — 예전에 `Zone` 에 `fx=` 를 안 쓰기로 한 이유였다.

발사체(`Projectile`)는 아직이다. **날아가는 동안 위치가 바뀌어** 효과의 고정된 시작·끝점으로는
따라갈 수 없다. 별건으로 남겼다.

## 캐릭터 크기가 판정에도 반영된다 (2026-11-17)

**게임 규칙이 바뀐다.** 저장 파일 형식은 그대로이고 **그대로 호환된다**.

그전까지 캐릭터 크기(50%~1000%)는 **보기 전용**이어서, 크게 키우면 몸이 겹쳐 보이는데도
공격이 닿지 않았다. 이제 이렇게 바뀐다:

- **몸 반지름**(드래곤·몬스터)은 크기를 **항상** 따라간다 — "겹쳐 보이면 맞는다"
- **몬스터 공격 사거리와 예고 범위**도 **항상** 따라간다
- **스킬 판정 반경**은 `dragon.txt` 에 `scale_with_size=yes` 를 적은 스킬만 따라간다.
  지금 켠 것은 광역과 효과 그림이 넓은 **5개**다 — 망령의 포효·저주의 안개·혼령 관통·
  망계의 숨결(망령룡), 어둠의 숨결(그림자룡)
- **스킬 사거리(`range`)는 커지지 않는다.** 1000% 에서 사거리가 10배가 되면 균형이 깨진다

크기가 100% 면 계산이 전부 x1 이라 **예전과 완전히 같다.** 균형 수치는 바뀌지 않았다.

## 그림자룡 — 스킬 효과 그림 2종 (2026-11-17)

게임 규칙은 바뀌지 않았다. 저장 파일도 **그대로 호환된다**.

- **그림자 가르기와 어둠의 숨결에 효과 그림이 붙었다.** 전처럼 도형만 그리지 않고 그림이
  발동 -> 지속 -> 잔류 세 단계로 재생된다. 좌우 뒤집기와 캐릭터 크기(50%~1000%) 보정은
  2026-11-17 에 들어온 그리기 쪽 변경을 그대로 따른다.
- 어스름 장막(보호막)·낙인·궁극기 충전 그림은 **아직 넣지 않았다.** 보호막은 생성·유지·흡수
  세 장인데 한 스킬에 시트 한 장만 들어가고, 낙인·궁극기는 게임에 그 기능이 없다.

## 망령룡 — 안개·침식 합치기와 스킬 효과 그림 (2026-11-16)

**스킬 구성이 바뀐다.** 저장 파일 형식은 그대로지만 **Lv5 칸이 가리키는 스킬의 뜻이 바뀐다**
(망령의 침식 -> 망계의 숨결). 2026-11-15 사람 결정을 따른 것이고, 안개를 지우지 않아
장착 칸 번호는 밀리지 않는다.

- **저주의 안개(Lv3)가 세졌다.** 없어진 망령의 침식의 수치를 가져왔다
  (재사용 12초 / 배수 1.3 / 반지름 140 / 사거리 340 / 지속 5초). 장판이 하나로 줄었다.
- **망계의 숨결(Lv5)이 생겼다.** 턱을 열어 전방으로 영혼 격류를 쏟는 직선 스킬이다
  (재사용 14초 / 배수 2.6 / 사거리 300 / 두께 70). 수치는 전부 임시값이다.
- **세 스킬에 효과 그림이 붙었다** — 혼령 관통·망자의 발톱·망계의 숨결. 전처럼 도형만 그리지
  않고 8프레임 그림이 발동 -> 지속 -> 잔류 세 단계로 재생된다. 효과는 드래곤이 보는 쪽으로
  뒤집히고 캐릭터 크기(50%~1000%)를 따라 같은 자리에 붙는다.

## 스킬 효과 — 좌우 뒤집기와 앞으로 밀기 (2026-11-16)

게임 규칙은 바뀌지 않았다. 저장 파일도 **그대로 호환된다**.

- **효과 그림이 좌우로 뒤집힌다.** 효과가 왼쪽으로 뻗으면 그림도 뒤집어 그린다. 방향은 드래곤이
  보는 쪽이 아니라 효과의 발동점 → 끝점으로 판정하므로, 터지는 지점이 곧 끝점인 `Burst`(포효 같은
  원형 효과)는 전처럼 뒤집지 않는다.
- **`fx_offset_x=` 가 생겼다.** 효과를 바라보는 쪽으로 미는 값이다(양수가 앞). 뒤집히면 방향도 같이
  뒤집힌다.
- **`fx_offset_y=` 의 뜻이 바뀌었다** — 화면 px 에서 **100% 기준 px** 로. 보기 크기 설정(50%~1000%)
  만큼 보정값도 함께 커진다. 1000% 에서 머리 위 보정이 몸통에 파묻히던 문제를 막는다.
  `fx=` 를 적은 스킬이 아직 없어 **깨지는 데이터는 없다**([구현 메모](implementation-notes.md) 참고).

## v1.9 — 보기 설정과 작업표시줄 꾸미기 (2026-11-16)

저장 파일은 **그대로 호환된다**(`ui.taskbarSkin` 키가 하나 늘었고, 모르는 키는 무시된다).

### 더한 것
- **캐릭터 크기를 1000%까지** 올릴 수 있다(전에는 200%). 그림만 커지고 맞는 거리·공격 범위는 그대로다.
- **Ctrl+Alt+D — 전부 숨기기.** 드래곤·상태창·메뉴가 한 번에 사라진다. 숨어 있어도 자동 사냥은 계속 돈다.
  트레이 메뉴의 "드래곤 숨기기"와 같은 기능이다.
- **작업표시줄 꾸미기.** 선택한 드래곤의 UI 스킨에 `taskbar.png` 가 있으면 작업표시줄 위에 그 띠를 덮는다.
  지금은 **망령룡**만 있다(`assets/ui/revenant/taskbar.png`). 클릭은 통과하고, 환경 설정에서 끌 수 있다.

### 고침
- **상태창·메뉴를 화면 가장자리 너머로 끌면 자리가 틀어지던 것.** 그리는 쪽에서만 잘라서,
  저장되는 좌표는 화면 밖 값이었다. 이제 저장되는 값 자체를 자른다.
- **트레이로 숨겨도 0.25초 뒤 다시 나타나던 것.** 전체화면 감시가 "사람이 숨긴 것"을 구분하지 못하고
  덮어썼다. 숨는 이유를 둘로 나눴다.

## CI·문서: 저장 공간 때문에 main 이 빨개지던 것 (2026-11-16)

**게임은 바뀌지 않았다.**

### 고침

- **산출물 업로드 실패가 더 이상 검사 결과를 가리지 않는다.** Actions 저장 공간이 가득 차면 업로드 단계만 실패하는데, 그 탓에 **빌드·테스트가 다 통과한 커밋에서도 main 이 빨갛게** 보였다(`d7f9a4f`, `29a644b`, `e52aa2e`). 업로드 단계에 `continue-on-error: true` 를 붙였다. 업로드 실패는 코드 문제가 아니다.
  - 맞바꾼 것: 묶음이 안 올라가도 초록으로 보인다. 받을 묶음이 없으면 공간을 비우고 그 커밋을 다시 돌린다.
- 쌓여 있던 산출물 중 종류별로 최신 하나만 남기고 **220MB 를 지웠다**(남은 4개 78MB). 다만 **GitHub 는 사용량을 6~12시간마다 다시 계산**해서 지운 직후에는 그대로 실패한다. 재계산 전까지는 위 `continue-on-error` 가 main 을 초록으로 지켜 준다.
- **저장 공간은 저장소가 아니라 계정 전체로 센다.** 이 저장소만 비워도 다른 저장소가 쓰고 있으면 계속 찬다. 계정 쪽에서 확인·조정할 곳은 [문서 하단](#저장-공간이-또-찰-때)에 적었다.

### 문서 최신화

- `README.md`·`CLAUDE.md` 의 버전 줄이 **v1.6 에 멈춰 있었다** → v1.8.
- **v1.8 항목이 11/15 묶음 아래에 끼어 있었다** → 11/16 자리로 올렸다. 변경 기록 맨 위에 "날짜 내림차순으로 쌓는다"를 적어 뒀다.
- **v1.6 이 두 개, v1.7 이 없었다** → 뒤의 "적 변종: 그림을 빌려 쓰기"를 **v1.7** 로 고쳤다.

### 저장 공간이 또 찰 때

1. 저장소 → Actions → 왼쪽 아래 **Storage** 또는 계정 **Settings → Billing → Storage** 에서 어느 저장소가 쓰고 있는지 본다.

## 문서: 탑 100층 결정 — 원소 보류·크레딧·상점·파티 조작 (2026-11-16)

**코드는 바뀌지 않았다.** 사용자 결정을 [기획서 10장](game-design.md#확정-탑-100층-확장-방향-2026-11-15)과 [설계안](tower-100-design.md)에 반영했다.

- **원소는 설계에서 뺐다.** 앞서 정한 드래곤 5원소·몬스터 원소를 지우고 사용자가 새로 설계한다. T5는 보류, T2에서 원소 저장 키를 만들지 않는다.
- **재화 이름은 크레딧.** 획득 기준과 상점 품목·가격은 사용자가 맡겨서 Claude가 임시값으로 정했다(설계안 4.4). 1 크레딧 = 가장 약한 몬스터 한 마리. 사냥 처치 `2 + 적 레벨 ÷ 5`, 자동 ×0.7, 탑 첫 돌파 `층 × 10`(중간 보스 ×30, 필드 보스 ×100), 재돌파 20%.
- **상점**: 드래곤 알(3,000부터 한 마리마다 +1,000, 가장 비쌈)·탑 물약(소·대 — **탑 안에서만, 한 번 오를 때 최대 2개, 마시는 데 1초**)·훈련서. 부활·사망 무효는 팔지 않는다. **UI 스킨은 팔지 않기로 했다**(사용자 결정).
- **필드 보스 파티는 1마리만 조작, 3마리는 자동.**
- **지역·보스 20종 확정.** 10층마다 지역 하나, 중간보스 10종·필드보스 10종과 코덱스 그림 규격(칸 512px, 부품 별도)을 새 문서 [`tower-100-bosses.md`](tower-100-bosses.md)에 적었다. 리치는 35층 중간보스로 옮긴다(T4). 첫 그림은 5층 고블린 족장으로 검증한다.

## 이슈 #47~#50 수정 (2026-11-16)

Windows에서 직접 실행하며 찾은 네 가지다. 함께 **바탕화면 사냥 방식을 정정**했다 — 탑 100층 설계안에 적었던 "클릭 사냥으로 교체"는 취소하고 **디펜스를 유지**한다(사용자 정정). 기획서 10장·설계안·CLAUDE.md 를 같이 고쳤다.

- **#47 "아래쪽에만"을 꺼도 전투를 시작하면 아래로 고정되던 것.** 사용자 결정으로 규칙을 바꿨다 — 싸우는 자리는 이 설정을 따른다. 켜면 맨 아래 띠, 끄면 화면 전체에서 싸우고 적은 왼쪽 밖에서 드래곤이 있는 높이 근처로 들어온다. 사냥 중에 바꿔도 바로 적용된다. 자동 사냥은 전부터 띠로 내려가지 않고 있었는데(시작 경로가 달랐다) 이제 같은 규칙을 쓴다(`Game::enterBattleArea`).
- **#48 전투를 시작하면 화면 전체가 살짝 어두워지던 것.** 키보드를 받는 동안 화면 전체를 칠하던 표시를 없앴다. 바탕화면 전투(직접·스킬 수동)를 시작하면 키보드가 저절로 켜져 필터처럼 보였다.
- **#49 아래쪽에서 드래곤·적이 작업 표시줄 밑으로 잘리던 것.** 띠 위치는 맞았는데 **그림을 판정 원의 가운데에 두어** 발이 원보다 아래(드래곤은 약 11px, 캐릭터 크기 2배면 약 56px)로 내려갔다. 이제 시트의 발(240/256 줄)을 판정 원의 아래 끝에 맞춘다. **판정·이동은 바뀌지 않고 그림이 발 기준으로 선다** — 그래서 캐릭터를 크게 키우면 위로 자란다.
- **#50 관리창·스킬창을 열면 프레임이 떨어지던 것.** 큰 창틀 그림(원본 1109×1382)을 매 프레임 9조각으로 줄여 그리던 비용으로 본다. 원인은 팀원 측정(#53)으로 확인됐다. 캐시는 **v1.8 의 `Renderer::drawPieceCached`(#54) 하나로 정리했다** — 이 PR 에서 넣었던 `cachedPiece` 는 #54 병합 때 그쪽으로 합쳐져 없어졌다.

## v1.8: UI 조각 캐시 (큐 12번 1단계) (2026-11-16)

**보이는 변화는 없어야 한다.** 같은 그림을 같은 자리에 그리되 **다시 계산하지 않는다.**

### 왜

큐 11번 측정에서 **UI 가 프레임의 55~93%** 였다([측정](implementation-notes.md#프레임-시간-측정-2026-11-16-큐-11번--사람이-windows-에서-쟀다)).
원인은 캐시가 하나도 없다는 것이었다 — `panel.png` 가 1109x1382 인데 9조각이라 한 번 그릴 때
`DrawImage` 가 9번이고, 전부 `ColorMatrix` 를 써서 GDI+ 의 빠른 경로를 못 탄다.
스킬 창은 줄이 7개라 한 프레임에 `DrawImage` 가 70번이 넘었다.

**큐 12번의 원래 전제는 틀렸다.** v1.4 가 "화면 전체를 매 프레임 지우고 합성하는 것"을 범인으로
적었는데, 측정에서 지우기 1.2ms + 합성 2.6ms 로 **합쳐 4ms 가 안 된다.** 거기를 고쳐도 소용없다.

### 무엇을

`drawPiece` 는 (그림, 목적지 크기, 투명도)의 **순수 함수**다 — 위치는 평행이동일 뿐이다.
그래서 결과를 **장치 픽셀 크기로 한 번 그려 두고 다음부터는 1:1 로 붙인다.** 1:1 이고
`ColorMatrix` 가 없으면 GDI+ 가 빠른 경로를 쓴다.

- **상태를 추적하지 않으므로 UI 가 낡을 위험이 없다.** 같은 입력이면 같은 그림이다.
- 장치 픽셀로 캐시한다 — `Graphics` 에 `ScaleTransform(dpi)` 이 걸려 있어서 논리 크기로 캐시하면
  붙일 때 또 배율이 먹어 다시 리샘플된다(느리고 흐리다).
- 한도: 256개 / 64MB. 넘으면 통째로 비운다. 1920x1080 보다 큰 조각은 캐시하지 않는다.
- `cfg::kUiPieceCache` 로 끈다. **보이는 차이가 나면 이것부터 꺼서 확인한다.**
- 측정 표시에 "UI 캐시 N개 · N MB" 줄을 더했다. **숫자가 멈추지 않고 계속 늘면 버그다**
  (키가 매 프레임 달라진다는 뜻).

### 아직 안 한 것

**글자는 그대로다.** `Renderer::text` 가 글자마다 `DrawString` 을 2번, `strongShadow` 면 5번
부르는 것은 이 변경이 건드리지 않았다. 스킬 창의 글자가 30개가 넘으므로 남은 비용의 상당 부분이
거기일 수 있다. **얼마나 줄었는지는 재 봐야 안다** — 글자 캐시는 결과를 보고 따로 한다.

### 사람이 확인할 것

1. **보이는 차이가 없는지.** 상태창·버튼·모달·체력바가 전과 같아야 한다.
   특히 체력바(부분 표시는 클립으로 한다)와 투명도가 다른 패널들.
2. **측정을 켜고 전후 숫자를 비교.** 같은 조건(측정 켠 상태)에서 재야 비교가 된다.
3. "UI 캐시" 숫자가 **어느 선에서 멈추는지.**
