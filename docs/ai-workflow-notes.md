# AI 작업 비용 기록과 개선

AI 도구로 개발할 때 드는 비용(토큰)을 줄이기 위한 기록이다. 측정 → 원인 → 조치 순으로 적는다.
새로 측정할 때마다 맨 위에 추가한다.

## 2026-11-16 밤 · **토큰의 66%는 "매 턴 다시 읽히는 지시문"이었다**

스킬 이펙트 적용 계획을 세운 세션(요청 43회)을 실측했다.

| 그룹 | 비중 |
|---|---|
| 지시문 (시스템 프롬프트 + 도구 목록 + `CLAUDE.md` + 첨부) | **66.2%** |
| 파일·명령 (`Bash` 28회 / `Write` 1 / `Edit` 1) | 20.4% |
| 대화 자체 (답변·사고 7.4 + 사용자 0.2) | 7.6% |
| GitHub·예약 연결 | 2.9% |
| 그 외 | 3.0% |

캐시 읽기 8,278,189 / 캐시 쓰기 100,689 / 출력 39,265 토큰. 비용 가중 약 123만 토큰분.

**원인**: 지시문은 턴마다 다시 읽히므로 43번 재읽혔다. **읽은 양이 아니라 주고받은 횟수가
비용을 정한다** — `CLAUDE.md` 의 "적게 주고받기"가 숫자로 확인됐다. 답변을 짧게 써서 아끼는
것은 7.6% 안에서의 다툼이라 거의 의미가 없다.

**조치**: `docs/archive/auto-queue-2026-11-16.md` 에 "주고받는 횟수를 줄이는 규칙" 6개를 넣었다
(명령 묶기 / 출력 걸러 받기 / 넓은 조사는 서브에이전트 / 큰 파일은 grep / 중간 보고 생략 /
안 쓰는 MCP 끄기). 자세한 기법 조사와 그날 생긴 문제 6건의 해결책은
[토큰 절약 정리](token-budget.md)와 [조사 원본](archive/token-notes-2026-11-16.md)에 있다.

**그 세션에서 실제로 틀린 것 두 개** (반복하지 않기):

1. **`&&` 로 묶다가 게이트를 건너뛰었다.** CI 폴링 루프 뒤에 머지 명령을 `&&` 로 이었는데,
   루프는 "확인 끝"으로 **정상 종료**하므로 CI 실패와 무관하게 머지가 실행됐다. PR 하나가
   CI 실패 상태로 머지됐다. → **판정을 종료 코드로 끌어올릴 것**
   (`echo "$R" | grep -q failure && exit 1` 뒤에 머지). **되돌릴 수 없는 동작(머지·푸시·삭제)은
   조회 명령과 묶지 않는다.** 토큰 절약과 게이트 준수는 충돌할 수 있다.
2. **도구 출력을 날것으로 받았다.** PR 변경 파일 415개 중 100줄을 그대로 받아 세션 끝까지
   context 에 지고 갔다. → `gh api` 는 `-q`, 목록은 `awk`·`sort -u`.
   **세어 보려면 세는 명령을 쓰고 목록을 가져오지 않는다.**

**적용하지 않은 것과 이유**: `CLAUDE.md` 축약(외부 벤치마크는 500토큰 아래로 줄여 91.9% 감소에
품질 저하 없음이라 하지만, 이 문서의 "깨지면 안 되는 핵심 규칙"이 매 턴 들어오는 값이 더 크다) /
context editing 의 도구 결과 지우기(지우는 행위가 프롬프트 캐시를 무효화한다 — 캐시 읽기 비중이
큰 이 규모에서는 손해일 수 있다. 손익분기 턴 수는 아직 계산하지 못했다) /
외부 훅 도구(수치의 1차 자료를 찾지 못했고 함께 쓰는 저장소에 훅을 넣는 리스크).

가득 차면 **빌드·테스트가 다 통과했는데도 업로드 단계가 실패해서 main 이 빨갛게 된다**(11/16 실제로 그랬다).

새 폴더를 `assets/` 에 추가할 때는 **게임이 읽는지**로 판단한다. 읽지 않는 자료는 `assets/references/`
아래에 두면 자동으로 묶음에서 빠진다. 다른 위치에 두면 두 워크플로를 모두 고쳐야 한다.

## 2026-11-14 (밤) · **"안 되는 것"으로 적어 둔 것 하나가 사실이 아니었다**

`src/win` 은 **이 환경에서 컴파일된다.** mingw-w64 로 GDI+ 까지 포함해 링크가 되고 20초쯤에
`.exe` 가 나온다. 아래 목록과 v0.6 기록이 "mingw 크로스 컴파일러도 설치되지 않는다"고 적고
있었는데, 그건 **`apt-get update` 를 먼저 하지 않아 패키지를 못 찾은 것**이었다. 그 한 줄 때문에
v0.6 이후 `src/win` 의 모든 검증이 CI 왕복으로만 이뤄졌다.

```bash
sudo apt-get update && sudo apt-get install -y mingw-w64
tools/check_win_build.sh          # 문법 검사 9초
tools/check_win_build.sh --link   # .exe 까지
```

**검사 도구는 결과물을 남긴다 — `git add -A` 전에 `git status --short` 를 본다.**
`tools/check_win_build.sh --link` 는 `dist/win-local/dragon_tower.exe`(3.7MB), `tools/check_static.py`
는 `build-cc/` 를 만든다. 세 회차가 각각 이걸 커밋에 집어넣었다(한 번은 푸시까지 갔다).
**둘 다 `.gitignore` 에 넣었으니 이제 걸리지 않는다** — 새 검사 도구를 만들면 그 도구의 작업
폴더도 같은 PR에서 `.gitignore` 에 적는다.

v0.6 의 CI 실패 셋을 전부 여기서 잡는다(실제로 `shellapi.h` 를 지워 확인했다).
자세한 것과 한계는 [`docs/quality-tools.md`](quality-tools.md) 1절.

**교훈**: "이 환경에서 안 된다"고 적을 때는 **무엇을 시도해서 어떻게 실패했는지**를 같이 적는다.
근거 없이 적힌 제약은 아무도 다시 시험하지 않고 그대로 굳는다.
(v0.2 의 "망령룡 원본이 LFS 에 있다고 넘겨짚고 시도조차 안 했다" 와 같은 종류다 —
그때 남긴 교훈이 "확인 전에 못 한다고 판단하지 말 것" 이었는데 또 걸렸다.)

## 2026-11-14 · 이 환경에서 안 되는 것 (추가)

- **Git LFS 업로드가 막혀 있다.** `git lfs pull`(받기)은 되지만 push는 S3(`github-cloud.s3.amazonaws.com`)로 가는데 프록시가 막는다. LFS로 묶인 경로(`assets/references/revenant-dragon/**`)에 새 파일을 넣으면 **푸시 자체가 실패한다.** 커밋에서 빼고 사람에게 올려 달라고 해야 한다.
- 브랜치 삭제도 여전히 막혀 있다(git refs 쓰기 금지).
- **`gh` 의 GraphQL 경로가 막혀 있다.** `gh pr list` 같은 명령이 `HTTP 403`으로 죽는다.
  REST로 쓴다 — `gh api "repos/1rkdwnsgh1/dragon-tower/pulls?state=open"`. CI 로그는 전처럼
  `gh run view <id> --log-failed`.
- **PR 본문·커밋 메시지를 셸 인자로 넘기지 않는다.** 백틱(`` ` ``)이 명령 치환으로 실행돼
  `command not found` 가 나고 그 단어들이 본문에서 빠진다. heredoc으로 파일에 쓴 뒤 파일을 넘긴다
  (`git commit -F 파일`, `gh api ... -F body=@파일`).
- **`main` 이 작업 중에 움직인다.** 두 사람이 같은 저장소를 쓴다. 실제로 한 세션이 상태를
  확인하는 동안 `main` 이 v1.4 → v1.5로 올라갔다. **긴 작업은 시작할 때와 푸시 직전에 각각 받는다.**
  에셋 폴더도 같다 — 파일 목록을 쓰기 직전에 한 번 더 확인한다(v1.4에서 없는 파일을
  스테이징하려다 실패했다).

## 2026-11-13 · v0.3~v0.7 (측정값 없음)

**비교할 수 있는 측정값이 없다.** 아래 v0.2 측정은 **같은 대화 안에서** 요청 156번째에 찍은 중간 스냅숏이고, v0.3~v0.7도 그 대화를 계속 이어서 했다. 그래서 "조치 전후"로 나눌 수가 없다. 조치의 효과를 숫자로 보려면 **버전 하나를 새 대화에서 처음부터 끝까지 하고 그 대화를 측정**해야 한다. 다음 버전에서 그렇게 해 보자.

숫자 없이 관찰된 것만 적는다 — 근거가 약하므로 효과의 증거로 쓰지 말 것:

- 코드 지도를 만든 뒤에는 `Renderer.cpp`·`World.cpp`를 큰 덩어리로 읽는 일이 없었다. 지도에서 함수 이름을 찾아 `grep` 하고 그 근처만 읽었다.
- 빌드·테스트를 `&&`로 이어 한 번에 실행했다. v0.2에서는 따로 실행했다.
- 그렇지만 **요청 횟수를 줄이는 쪽은 잘 안 됐다.** v0.3의 크기 보정, v0.6의 CI 실패 세 번처럼 결과를 눈으로 확인해야 하는 작업과 CI 왕복은 횟수가 그대로 들었다. 비용의 3분의 2를 차지하는 항목이 여기라서, 코드 지도만으로는 총액이 크게 줄지 않았을 가능성이 높다.
- 되돌리기(원인 4)는 v0.3에서 또 발생했다. 변환 배율 문제로 세 번 다시 변환했다. 이번에는 사람의 결정이 아니라 **결과를 측정하지 않고 눈대중한 것**이 원인이었다.

### 그래서 다음에 할 것

- 버전 하나를 새 대화에서 끝내고 측정해 v0.2와 비교한다
- **결과를 눈으로 확인해야 하는 작업**(이미지 변환, 크기 보정)은 비교 이미지를 한 번에 여러 개 만들어 왕복을 줄인다
- **CI 왕복**을 줄이는 것이 남은 가장 큰 항목이다. `src/win`을 고치면 푸시 전에 헤더 포함·타입 모호성·정의 순서를 훑는다 ([팀원용 지침](team-ai-prompt.md) 3절)

### 원인

1. **요청 횟수가 비용을 지배한다.** 기본 지시문이 3분의 2를 차지하는데, 이건 **무엇을 했는지와
   무관하게 요청 한 번마다 똑같이 든다.** 156번 주고받은 것이 가장 큰 비용이었다.
   한 번에 여러 일을 묶었다면 같은 결과를 더 적은 횟수로 낼 수 있었다.
2. **코드 위치를 몰라 넓게 읽었다.** 구조를 파악하려고 `Renderer.cpp`(약 1060줄),
   `World.cpp`(약 680줄), `App.cpp`(약 480줄)를 큰 덩어리로 읽었다. 어디에 무엇이 있는지 적힌
   문서가 없어서 생긴 비용이고, 사람이 새로 합류할 때도 똑같이 드는 비용이다.
3. **명령을 잘게 나눠 실행했다.** `Bash` 44번, `Edit` 42번. 빌드와 테스트, 확인을 따로 실행하거나
   같은 파일을 여러 번 열었다.
4. **결정을 되돌리며 다시 작업했다.** 캐릭터 기본 방향을 왼쪽으로 정해 문서·템플릿·스크립트를
   만든 뒤, 팀이 이미 오른쪽으로 작업 중이라는 것을 알고 전부 되돌렸다.
   사람이 정해야 할 것을 **처음에 모아서 물었다면** 피할 수 있었다.

### 남은 개선 (아직 안 함)

- **큰 파일 쪼개기.** `Renderer.cpp` 1060줄은 화면별로 나누면(월드/HUD/모달) 필요한 부분만 열 수 있다.
  다만 지금 당장은 코드 지도로 충분하고, 쪼개는 작업 자체도 비용이 든다. 더 커지면 하는 것이 좋다.
- **작업 단위를 크게 잡기.** "A를 하고, 되면 B를 하고, 안 되면 알려 줘"처럼 한 번에 여러 단계를
  맡기면 주고받는 횟수가 준다. 반대로 단계마다 확인받으면 안전하지만 비용이 는다.
  **되돌리기 어려운 일(배포, 파일 삭제)은 확인받고, 되돌리기 쉬운 일은 묶어서 맡기는 것**이 기준이다.
- **새 대화로 나누기.** 한 대화가 길어지면 앞의 내용이 계속 따라다닌다. 주제가 바뀌면
  (기획 논의 → 구현) 새 대화를 시작하는 편이 싸다.

## 탑 층 난이도를 잴 때 (2026-11-15, 큐 3번)

**등반 중의 "그 층에서 잃은 체력"으로 층 난이도를 맞추려 하면 헛돈다.** 그 숫자는 들어갈 때의
체력(앞 층 결과 + 층 돌파 회복 30%)에 섞여 있어서, 쉬운 층이 어려워 보이고 어려운 층이 쉬워 보인다.
이번에 그걸 모르고 두 번 맞춰 보다가 버렸다.

**층 하나만 담은 `floors.txt` 를 만들면 그 층이 1층이 되어 온전한 체력에서 재진다.** 코어를
고칠 필요가 없다. 에셋 폴더를 복사하지 말고 `dragons`·`enemies` 를 심볼릭 링크로 묶은 임시
폴더를 만들어 `balance_sim <그 폴더> floors ...` 로 돌리면 한 번이 1초 안에 끝난다.
측정값과 표는 [`implementation-notes.md`](implementation-notes.md) "탑 10층의 층별 난이도" 절에 있다.
