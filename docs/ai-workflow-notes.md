# AI 작업 비용 기록과 개선

AI 도구로 개발할 때 드는 비용(토큰)을 줄이기 위한 기록이다. 측정 → 원인 → 조치 순으로 적는다.
새로 측정할 때마다 맨 위에 추가한다.

## 2026-11-14 · 이 환경에서 안 되는 것 (추가)

- **Git LFS 업로드가 막혀 있다.** `git lfs pull`(받기)은 되지만 push는 S3(`github-cloud.s3.amazonaws.com`)로 가는데 프록시가 막는다. LFS로 묶인 경로(`assets/references/revenant-dragon/**`)에 새 파일을 넣으면 **푸시 자체가 실패한다.** 커밋에서 빼고 사람에게 올려 달라고 해야 한다.
- 브랜치 삭제도 여전히 막혀 있다(git refs 쓰기 금지).
- **`gh` 의 GraphQL 경로가 막혀 있다.** `gh pr list` 같은 명령이 `HTTP 403`으로 죽는다.
  REST로 쓴다 — `gh api "repos/1rkdwnsgh1/dragon-tower/pulls?state=open"`. CI 로그는 전처럼
  `gh run view <id> --log-failed`.
- **PR 본문·커밋 메시지를 셸 인자로 넘기지 않는다.** 백틱(`` ` ``)이 명령 치환으로 실행돼
  `command not found` 가 나고 그 단어들이 본문에서 빠진다. heredoc으로 파일에 쓴 뒤 파일을 넘긴다
  (`git commit -F 파일`, `gh api ... -F body=@파일`).
- **`main` 이 작업 중에 움직인다.** 팀원 3명이 같은 저장소를 쓴다. 실제로 한 세션이 상태를
  확인하는 동안 `main` 이 v1.4 → v1.5로 올라갔다. **긴 작업은 시작할 때와 푸시 직전에 각각 받는다.**
  에셋 폴더도 같다 — 파일 목록을 쓰기 직전에 한 번 더 확인한다(v1.4에서 없는 파일을
  스테이징하려다 실패했다).

## 2026-11-13 · v0.3~v0.7 (측정값 없음)

**비교할 수 있는 측정값이 없다.** 아래 v0.2 측정은 **같은 대화 안에서** 요청 156번째에 찍은 중간 스냅숏이고, v0.3~v0.7도 그 대화를 계속 이어서 했다. 그래서 "조치 전후"로 나눌 수가 없다. 조치의 효과를 숫자로 보려면 **버전 하나를 새 대화에서 처음부터 끝까지 하고 그 대화를 측정**해야 한다. 다음 버전에서 그렇게 해 보자.

숫자 없이 관찰된 것만 적는다 — 근거가 약하므로 효과의 증거로 쓰지 말 것:

- 코드 지도를 만든 뒤에는 `Renderer.cpp`·`World.cpp`를 큰 덩어리로 읽는 일이 없었다. 지도에서 함수 이름을 찾아 `grep` 하고 그 근처만 읽었다.
- 빌드·테스트를 `&&`로 이어 한 번에 실행했다. v0.2에서는 따로 실행했다.
- 그렇지만 **요청 횟수를 줄이는 쪽은 잘 안 됐다.** v0.3의 크기 보정, v0.6의 CI 실패 세 번처럼 결과를 눈으로 확인해야 하는 작업과 CI 왕복은 횟수가 그대로 들었다. 비용의 3분의 2를 차지하는 항목이 여기라서, 코드 지도만으로는 총액이 크게 줄지 않았을 가능성이 높다.
- 되돌리기(원인 4)는 v0.3에서 또 발생했다. 변환 배율 문제로 세 번 다시 변환했다. 이번에는 사람의 결정이 아니라 **결과를 측정하지 않고 눈대중한 것**이 원인이었다.

### 그래서 다음에 할 것

- 버전 하나를 새 대화에서 끝내고 측정해 v0.2와 비교한다
- **결과를 눈으로 확인해야 하는 작업**(이미지 변환, 크기 보정)은 비교 이미지를 한 번에 여러 개 만들어 왕복을 줄인다
- **CI 왕복**을 줄이는 것이 남은 가장 큰 항목이다. `src/win`을 고치면 푸시 전에 헤더 포함·타입 모호성·정의 순서를 훑는다 ([팀원용 지침](team-ai-prompt.md) 3절)

### 원인

1. **요청 횟수가 비용을 지배한다.** 기본 지시문이 3분의 2를 차지하는데, 이건 **무엇을 했는지와
   무관하게 요청 한 번마다 똑같이 든다.** 156번 주고받은 것이 가장 큰 비용이었다.
   한 번에 여러 일을 묶었다면 같은 결과를 더 적은 횟수로 낼 수 있었다.
2. **코드 위치를 몰라 넓게 읽었다.** 구조를 파악하려고 `Renderer.cpp`(약 1060줄),
   `World.cpp`(약 680줄), `App.cpp`(약 480줄)를 큰 덩어리로 읽었다. 어디에 무엇이 있는지 적힌
   문서가 없어서 생긴 비용이고, 사람이 새로 합류할 때도 똑같이 드는 비용이다.
3. **명령을 잘게 나눠 실행했다.** `Bash` 44번, `Edit` 42번. 빌드와 테스트, 확인을 따로 실행하거나
   같은 파일을 여러 번 열었다.
4. **결정을 되돌리며 다시 작업했다.** 캐릭터 기본 방향을 왼쪽으로 정해 문서·템플릿·스크립트를
   만든 뒤, 팀이 이미 오른쪽으로 작업 중이라는 것을 알고 전부 되돌렸다.
   사람이 정해야 할 것을 **처음에 모아서 물었다면** 피할 수 있었다.

### 남은 개선 (아직 안 함)

- **큰 파일 쪼개기.** `Renderer.cpp` 1060줄은 화면별로 나누면(월드/HUD/모달) 필요한 부분만 열 수 있다.
  다만 지금 당장은 코드 지도로 충분하고, 쪼개는 작업 자체도 비용이 든다. 더 커지면 하는 것이 좋다.
- **작업 단위를 크게 잡기.** "A를 하고, 되면 B를 하고, 안 되면 알려 줘"처럼 한 번에 여러 단계를
  맡기면 주고받는 횟수가 준다. 반대로 단계마다 확인받으면 안전하지만 비용이 는다.
  **되돌리기 어려운 일(배포, 파일 삭제)은 확인받고, 되돌리기 쉬운 일은 묶어서 맡기는 것**이 기준이다.
- **새 대화로 나누기.** 한 대화가 길어지면 앞의 내용이 계속 따라다닌다. 주제가 바뀌면
  (기획 논의 → 구현) 새 대화를 시작하는 편이 싸다.
